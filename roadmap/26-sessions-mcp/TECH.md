# Feature 26 — Sessions & Projects MCP: technical spec

Behavior: see `PRODUCT.md` (invariants referenced as P#N below).

## Context

twarp has two built-in MCP servers with an established shape this feature clones:

- `app/src/browser_mcp.rs` — the reference. `BrowserMcpRuntime::start` (255–269) builds a dedicated 1-worker tokio runtime + root `CancellationToken`; `start_server` (293–350) binds an rmcp `SseServer` on `127.0.0.1:0` (`/sse` + `/message`), one service instance per SSE connection via `with_service`. `session_server_url` (272–289) lazily creates one listener per Claude session, stamping `scope_session_id` on each service.
- `app/src/computer_control/mcp.rs` — same shape (694–783); also the reference for main-thread↔runtime handoff and for the pane-header indicator/kill-switch UI that provenance badges (P#22) will mirror.
- Injection: `claude_mcp_config_json` (`app/src/claude_code_view.rs:12376-12414`) merges registry + built-in server configs → `--mcp-config` (`crates/claude_code/src/driver.rs:245`). **Codex gap**: `codex_config_overrides` (`claude_code_view.rs:3724-3728`) passes registry-only config to `thread/start` (`crates/claude_code/src/codex/mod.rs:225,233`); built-ins are never injected (P#20).
- Pane creation: `open_claude_code_tab` (`app/src/workspace/view.rs:13153-13182`) = `add_terminal_tab` + `open_claude_code_pane` (13385); `create_project_chat_in_directory` (19822) already opens a chat inside a project.
- Sessions stores: `crates/claude_code/src/sessions.rs` (`StoredSession`: id/title/timestamp/jsonl_path/provider; `list_sessions_for`, `load_history`) and `codex/sessions.rs` (reads `session_meta` head for id+cwd, mtime cache).
- Status: computed in `ClaudeCodeView` — `ConversationStatus` (`claude_code_view.rs:4540-4577`), attention transitions (3925–4018), deferred completion (`maybe_fire_deferred_completion` 4598+), background work (`has_active_background_work` 4582). This is the single source `list_sessions` status must share (P#4, P#11).
- Message submission: `submit_message` (`claude_code_view.rs:3130`) / `send_user_message` driver path — `create_chat`'s prompt goes through this, not PTY bytes.
- Projects: `ProjectManagementModel` (`app/src/projects.rs:28`), `create_project(NewProjectSource, …)` (`view.rs:19674`).

## Proposed changes

New module `app/src/sessions_mcp.rs` + `app/src/sessions_mcp/` submodules, cloned from the browser bridge shape: `SessionsMcpBridge` (main-thread handle), `SessionsMcpRuntime` (tokio runtime + listeners), `SessionsMcpServer` (per-connection rmcp service, `#[tool_router]`).

**Registry facade (26b — as built).** The MCP runtime cannot touch views directly. `sessions_mcp::registry::SessionRegistry::global()` is a process-global `Mutex<HashMap>` (the codex sessions-cache pattern rather than a twarpui model — no watch channels needed until 26c's events) mirroring, per live session: id, provider, cwd, title, status, last-activity, flat transcript. Depth/origin/project columns land with 26d spawning. `ClaudeCodeView` publishes through `emit_tab_status_changed` (which wraps every former `TabStatusChanged` emission), at the end of `ingest_event`, at construction, and on resume re-key; `Drop` removes the row. The `ConversationStatus` computation was extracted into the pure `sessions_mcp::status::conversation_status(StatusInputs)` shared by `tab_status()` and the registry publisher (P#4 by construction; `session_status` folds it into the five-value MCP enum).

**Transcript access (26b — as built).** `get_transcript` (P#6–8): the registry holds, per live session, an append-only `Vec<FlatTranscriptItem>` (index, role, text). Rather than hooking each `TranscriptEvent`, the publisher re-projects `Transcript::items()` via `flatten_transcript` and the registry appends only the tail past its stored prefix — still-streaming assistant/thinking items end the projection (held back until final) so a served index's content never changes; tool items project name+input, fixed at creation. Past sessions: Claude replays `load_history` through a `Transcript` and flattens identically; Codex maps the rollout's `event_msg` lines (`user_message`/`agent_message`/`agent_reasoning`) directly — there is no rollout replay parser (`sessions_mcp/store.rs`). All-cwd store listings were added as `sessions::list_all_claude_sessions()` (cwd read from the jsonl's own `cwd` field) and `codex::sessions::list_all_sessions()`. `list_projects` reads `ProjectManagementModel` on the main thread via the bridge's `ModelSpawner`; projects have no persisted color (color is per-tab), so `color` is null and `session_count` is the stored-session count for the project's directory.

**Events (26c — as built).** Per-session `tokio::sync::broadcast::Sender<SessionEvent>` (`Item(FlatTranscriptItem)`, `Status(SessionStatus)`, `Closed`; capacity 256) lives in each registry row, fed inside `publish` (appended tail → `Item`s, status change → `Status`) and `remove` (→ `Closed`), all under the registry lock — no new publish points and no main-thread hops (wasm builds compile the registry without the channel via cfg gates). `SessionRegistry::subscribe`/`subscribe_all` capture receiver + current status + last index + last assistant text atomically, so "already terminal" checks have no race window. The transport-free semantics live in `sessions_mcp/events.rs`: `forward_watch_events` turns a subscription into `WatchNotification` JSON payloads (`{type: "session_event", event: item|status|closed, …}`) which `watch_session` drains onto the SSE peer as `notifications/message` (rmcp `notify_logging_message`, logger `twarp-sessions`; server capabilities now advertise logging) — a failed notify drops the sink and unwinds the forwarder, and a session that never emits again still terminates it via `Closed` (P#29). `wait_for_completion` fans each target's receiver into one mpsc and `tokio::select!`s it against `tokio::time::sleep` (default 300s, hard cap 3600s; distinct `timed_out` result per P#10); `"any"` = `subscribe_all` at call time (sessions created later are not targets). P#11 comes free: the registry only flips to `done_*` when the view's deferred-completion fires. Lagged receivers (`RecvError::Lagged`) never wedge or replay stale backlog: the handler `resubscribe()`s to the live tail, resyncs missed items from `transcript_since(last_index)` + current `status_of`, and an index guard filters overlap — a replayed stale done-status can therefore never resolve a wait on a session that resumed. Closed panes resolve waits as `done_error` + `reason: "closed"` (P#12), with the last assistant text tracked in the fan-in task so it survives row removal.

**Spawning + projects (26d — as built).** `create_chat` runs its main-thread half through the bridge's existing `ModelSpawner` (that channel *is* the SpawnRequest hop; no second channel was needed). Validation order on the main thread: cwd `is_dir` (invalid-argument), provider parse, named project exists (invalid-argument, never implicitly created), then `SessionRegistry::try_reserve_spawn(session_id, parent, cap)` — cap counting + depth computation + origin insertion happen under the one registry lock, so N racing calls admit at most `cap` (P#28; the reservation entry itself holds the slot until the pane publishes, and `remove` releases it). "Running" for the cap = registry status `Running`, or reserved-but-unpublished. Cap default 4 via the `agent.sessions_mcp.spawn_cap` setting (no UI row); depth refuses at 3 (`spawn::MAX_SPAWN_DEPTH`), user panes are depth 0. The new session id is minted *before* the pane and pinned into it via a new `LaunchOptions::pinned_session_id`, so `create_chat` returns it immediately (P#13). Spawn recipe: `Workspace::open_spawned_agent_chat` = `add_terminal_tab` + a new `open_claude_code_pane_with_launch` (refactored out of `open_claude_code_pane`, returns the view); the prompt rides in `LaunchOptions.prompt`, which enters the same first-turn submit path as the composer (`begin_session(OutgoingMessage)`) — never PTY bytes. A `project` argument files the new tab under the project (`tab.project_root`, the `ExistingFolder` tail) rather than routing through `create_project_chat_in_directory` (which is bound to an existing project tab's pane-group id). `SpawnOrigin { parent_session_id, parent_label, depth }` lives on the view, republishes into the registry row (`list_sessions` gains `spawned_by`/`spawn_depth`), renders as a passive header chip next to the computer-control indicator (`render_spawn_origin_chip`, "from: <parent title>" / "external: <label>"), and persists as JSON in a new `claude_code_panes.spawn_origin` column (migration `2026-07-31`, snapshot field on `ClaudeCodePaneSnapshot`) so the badge survives restore (P#22). In-pane parent = the tool's `scope_session_id` (label from the registry title); external callers get depth 1 with label "external" (no consumer-naming mechanism exists yet — the token carries no identity; the unscoped in-app fallback endpoint is labeled "in-app"). Nothing touches permission plumbing (P#26). `create_project` validates name/cwd, treats an existing project for the same (canonicalized) folder as the duplicate error, then calls the UI's `create_project(NewProjectSource::ExistingFolder…)` path plus `set_project_name`; a `color` argument is accepted and ignored (projects have no persisted color — see P#18 note).

**External listener (26d — as built).** Second listener in the same runtime (`ListenerKind::External`), fixed configurable port (default 8377, `agent.sessions_mcp.external_port`), bound to 127.0.0.1 only, serving the same `SessionsMcpServer` tool set. Axum `middleware::from_fn(external::require_bearer_token)` checks `Authorization: Bearer` against the token file (`0600`, `data_dir()/sessions_mcp_external_token`, generated on enable) — the file is **re-read per request**, so Regenerate invalidates the old token immediately with no cache to flush. Unauthorized requests get a structured 401 JSON body `{error: {code: "unauthorized"}}` (P#27); "surface-disabled" needs no tool-level error because a disabled listener is simply not bound. Off by default behind `agent.sessions_mcp.external_enabled`; the bridge observes `AgentSettings` and reconciles (enable → ensure token + bind; disable/port-change → cancel the listener's child token, severing live watchers, P#21/12). Bind failure (port conflict) → `ExternalListenerState::Failed` on the bridge, rendered as an error line on the Agents settings page (P#30). Settings UI (Agents page, "Sessions" section): the toggle, a port field (persisted only when parseable), the token file path display, and a Regenerate button.

**Codex parity (26e — as built).** Codex's `mcp_servers.<name> = { url }` config speaks the MCP *streamable HTTP* transport, not the legacy SSE the built-in endpoints serve — and the pinned rmcp (warpdotdev fork, 0.10.0) ships a `StreamableHttpService` server, so no stdio→SSE proxy was needed. `app/src/mcp_streamable_http.rs` hosts any built-in service over streamable HTTP on its own 127.0.0.1 ephemeral port (`/mcp`); each bridge grew a `session_http_servers` twin of its per-session SSE map (`session_http_server_url` + `codex_config_json_for_session`, same `scope_session_id` semantics — one service instance per MCP session, so per-connection state like the browser's bound pane behaves identically). `claude_code_view.rs`'s `codex_config_overrides_json(&self.session_id, …)` is `claude_mcp_config_json`'s twin: registry `codex_config_overrides` first, then the three built-ins (computer-control gated on `platform_supported()`), built-ins winning name collisions via the shared keyed `merge_mcp_servers`. Scoping key is the pane's `session_id` — the same key the sessions registry publishes under for both providers. Unlike Claude, a failed scoped HTTP start does not fall back to a shared unscoped endpoint (an unscoped endpoint can't carry the caller's identity); the server is simply not injected. Codex views publish into the registry identically — status inputs come from the shared `TranscriptEvent` seam so no per-provider divergence (P#7, 20).

**26f fleet adoption (as built).** Lives entirely in `fleet/fleet.py` (+ tests in `fleet/test_fleet_policy.py`); no app changes. `ux_drive_gate` now prefers the sessions-MCP surface over uidrive CGEvent injection, with uidrive/screenshots kept for pixel capture and as full fallback. Pre-seed before launch (`_ux_seed_mcp`): debug builds run the Oss channel, where `data_dir() == config_local_dir() == ~/.twarp-oss` and the `settings_file` cargo feature is default-on, so the fleet appends an `[agent.sessions_mcp]` table (`external_enabled = true`, `external_port`, default 8377 / `config.ux_mcp_port`) to `~/.twarp-oss/settings.toml` iff no `agent.sessions_mcp` keys exist, and mints a `0600` token at `~/.twarp-oss/sessions_mcp_external_token` iff absent — the bridge applies these settings at startup and `ensure_token` keeps a pre-existing non-empty token, so no UI enable is needed. Preflight after launch (`ux_mcp_probe` + pure `ux_mcp_decision`): a token-less `curl` of `http://127.0.0.1:<port>/sse` must return **401** (the bearer middleware) and the token file must be non-empty; any failure → the unchanged uidrive path with a logged reason (verdict parsing untouched). When ready, the `claude -p` driver gets `--mcp-config` built by the pure `ux_mcp_config(port, token)` (`{"type":"sse","url":"http://127.0.0.1:<port>/sse","headers":{"Authorization":"Bearer <token>"}}` under `mcpServers.twarp-sessions`); for a remote display pod an `ssh -N -L` forward on a fresh local port spans the driver's lifetime (the listener is 127.0.0.1-only). The drive prompt grows a `{mcp}` slot (`UX_MCP_PROMPT_SECTION`) telling the driver to prefer `list_sessions`/`get_transcript`/`create_chat`/`wait_for_completion` for agent flows while keeping the shot script for visual verdicts and `act` as in-drive fallback. Provenance: `_stamp_ux` level is `live-mcp` vs `live`; `ux_level_is_live` treats both as live in `write_run_report`'s merged-without-live-UX risk check. Acceptance is a full live fleet UX-gate round over this surface (owner/fleet run).

## Testing and validation

- Unit (`app/src/sessions_mcp/`, run via nextest on CI — local presubmit is unreliable on this machine): status projection parity (P#3–4) table-tests over `conversation_status` inputs; transcript index stability under concurrent append/read (P#8); cap/depth race tests with N racing spawn requests (P#23–24, 28); token middleware accept/reject/regenerate (P#21).
- Store mapping tests: Claude jsonl and Codex rollout fixtures → identical `TranscriptItem` shape (P#7).
- Manual smoke per phase (launch via `./script/run`, verify in-app — the keybinding/UI rule applies):
  - 26b: from a Claude pane, ask the agent to call `list_sessions`/`get_transcript`/`list_projects`; cross-check against sidebar and tab states.
  - 26c: `wait_for_completion` from pane A on pane B while B runs a long turn with a background script — checkmark and tool return must coincide (P#11); close B mid-wait → `closed` (P#12).
  - 26d: in-pane `create_chat` (badge, cap error at 5th, depth error at 3), external `curl -H "Authorization: Bearer …"` create+wait round-trip, bad token rejected, toggle-off severs a live watch; `create_project` appears in sidebar.
  - 26e: repeat the 26b/26d smokes from a Codex pane.
  - 26f acceptance: one full fleet UX-gate round over the new surface (P: Fleet adoption section).

## Parallelization

Mostly sequential — 26c/26d/26e all build on 26b's registry, and each phase is one reviewable PR per the repo's flow. Within 26d, the external listener + settings UI is separable from spawn/projects; if wall-clock matters, run two worktree agents (`.claude/worktrees/26d-spawn` on `feat/26d-spawn`, `.claude/worktrees/26d-external` on `feat/26d-external-listener`), owner-per-file: spawn agent owns `workspace/view.rs` + pane persistence; listener agent owns `sessions_mcp/external.rs` + `settings_view`. Merge spawn first; listener rebases. 26e can start in parallel with 26c (touches only the Codex config path + a proxy, not the registry internals).

## Risks and mitigations

- **Codex MCP transport unknown** (SSE vs stdio-only): resolved at the top of 26e before wiring; the stdio→SSE proxy fallback is scoped above so it can't stall the phase.
- **Main-thread publish points drift**: status parity is enforced by sharing one pure function and publishing at the repaint sites; a debug assertion comparing registry status to rendered status in dogfood builds catches drift early.
- **External surface = local RCE-adjacent**: mitigations are the token file perms, fixed localhost bind, off-by-default setting, cap/depth, and visible provenance. No auth on the in-app ephemeral-port servers is pre-existing and unchanged here.
- **Feature 18 transcript churn**: the flat `TranscriptItem` projection is the compatibility layer; only the projection function may need updating.
